# Review State Sidecar Schema

`<plan>.review-state.yaml` の正本。plan-writing / code-review-plan-loop が seed を書き、plan-refinement-loop が読んで状態遷移させる。ここに定義するのは**3スキルで共有する5キー**だけで、orchestrator 専用キー（`phase` / `iteration` / `last_investigation` / `applied_fixes` / `oscillation_log` 等）は plan-refinement-loop の `## State` が持つ。

- `document_type` — 値の定義は `plan-doctrine.md` の 文書型 節、キー欠落時の解決規則は plan-refinement-loop の Procedure 冒頭が在処。ここでは再掲しない。producer は plan-writing / code-review-plan-loop で、プランに添えるサイドカーへ必ず書く。
- `open_needs_user` — ユーザーにしか決められない未解決の問い。
  - producer: plan-refinement-loop（NEEDS-USER クラスの指摘、追加の finding-verifier でも決着しなかった事実、エスカレートした反復）、code-review-plan-loop（追加の finding-verifier でも決着しなかった事実、REFUTED / UNVERIFIABLE 由来の価値・スコープ・リスク姿勢の問い、carry した 見送り の前提が今ラウンドの差分で崩れたもの、振動ガードが検出した逆操作）、plan-writing（起案時に確定しなかった判断）。
  - 形式: `{ finding: "<一行要約>", location: "<逐語アンカー>", reason: "<NEEDS-USER クラス | 追加検証でも決着しなかった事実 | 未確定 | エスカレートした反復>", options: [ { label: "A", proposal: "<案>", pros: "<利点>", cons: "<欠点>" } ], pivot: "<判断が分かれる点>" }`。`options` / `pivot` は提示の形式（`finding-criteria.md` の 質問の出し方 節）をそのまま持つキー。**問いを提示するターンで記録・更新するエントリでは必須**（`/clear` 後の再開で逐語再提示でき、選択肢の書き直しにならない）。省略できるのは未提示のまま書かれるエントリだけで、キーの不在が未提示の印。
- `rejected` — レビュー指摘の却下（事実誤認）、ユーザーの見送り、code-review-plan-loop が Minor/Nit を落とした Measurement 不一致の記録。**ユーザー確定の見送りはプラン本文の1行と併記**し、起案時に不採用にした代替案は本文の1行のみ（使い分けは `plan-doctrine.md` の姿勢 節）。形式: `{ finding: "<一行要約>", reason: "REFUTED: <反証>" }` または `{ finding: "<一行要約>", reason: "見送り（ユーザー判断: <一言>）" }` または `{ finding: "<一行要約>", reason: "測定不一致: <期待出力と生出力の食い違いを一言>" }`（3 つ目は code-review-plan-loop の Normalize が書き、次ラウンドの carry 除外の対象。turn-end の 却下 には数えない）
- `filed_issues` — スコープ外指摘として起票した issue 番号。起票手順は `issue-filing.md`。
- `verified_facts` — 実際に検証した**中立な外部事実**と、Measurement の結果（実行して一致・不一致、および実行せず不成立と判定したもの）のみ。producer は plan-writing（起案時に検証した事実の seed）と code-review-plan-loop / plan-refinement-loop（finding-verifier verdict の `SOURCES` の追記と、Measurement の結果）。例: `"ReactiveUI 19.5: WhenActivated requires IActivatableViewModel (confirmed via Context7)"`。記録の形式は `measurement-run.md` の 照合 節 が正本。指摘・修正履歴は書かない — 例外は測定記録の `location` / `iteration` の2フィールドで、無効化判定に使う orchestrator 専用として持つ（渡す前の扱いは plan-refinement-loop の step 2 手順 3）。seed した事実は下流で再検証されないため、未検証の推測を入れると検証層を素通りする。

共通規則: 空リストは `[]` を明示。`:` `#` `§` や先頭記号を含む文字列は引用符で囲む。キー名は変えない。`rejected` / `filed_issues` / `verified_facts` は Round をまたいで累積する（`verified_facts` の測定結果・不成立エントリを除く — 突合キー `location` / `iteration` が Round をまたがないため、carry すると旧プランへの測定が新プランの指摘を封じる。`rejected` の `測定不一致:` エントリは対象外で、従来どおり carry する）。seed（plan-writing / code-review-plan-loop が書くもの）は上記5キーのみで `phase` を書かない（`phase` の不在が seed の印）。
