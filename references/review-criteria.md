# レビュー指摘の規約

生成側（standard-code-review / deep-code-review / simplification-review / plan-investigator）と受け手（code-review-to-plan / plan-refinement-loop / finding-verifier）の共通規約。

## 指摘の形

- フィールドは ID / 重大度 / 場所 / 問題 / 根拠 / クラス。
- 場所 は逐語アンカー。`path:line` は補助。
- 問題 と 根拠 を融合させない — finding-verifier は 根拠 だけを独立に検証する。
- 起きえないことは指摘ではない。防御を足す提案がその類なら報告しない。「想定が要るか」自体を問いたいときだけ NEEDS-USER で聞く。
- 仮説だけの指摘は成立しない。外部ツールの挙動を前提にした「壊れうる」指摘は、再現・実測・記録された失敗・一次ソースのいずれかを 根拠 に持つときだけ成立する。
- 行動予測型の指摘（実行者はこう読む・こう動く）には `Measurement` を添える。添えられない Minor / Nit は報告しない。Critical / Major は添えなくても報告してよいが、裁定は実測を経てから行う。

## 重大度

| 重大度 | 帰結 | コード差分での読み | プラン文書での読み |
|---|---|---|---|
| Critical | 放置すると回復困難な実害 | データ損失、セキュリティ侵害、本番停止・データ破壊 | そのまま実行すると破壊的（誤った対象、取り返しのつかない手順） |
| Major | 通常の実行経路で誤ったものが動く・作られる | 通常の入力で機能が壊れる、バグが残る（対症療法・横展開漏れ）、呼び出し側の契約破壊 | 実装セッションが誤ったコードを書く・詰まる（誤ったパス / API / シグネチャ、必須手順の欠落、節どうしの矛盾） |
| Minor | 通常の経路では起きない、または動作が変わらない | 異常返り値・空 / `null`・切り詰め等への防御不足、重複、再発明、回帰テスト欠落、曖昧な契約 | 実装セッションが書くものを変えない（冗長、解決可能な古い参照、明確さ） |
| Nit | 表記・語彙のみ | 命名、書式 | 言い回し（設計のやり直しは Nit ではない） |

- 軸は「放置したときの帰結」×「通常の実行経路で踏むか」の 2 つ。実在確度と修正コストは混ぜない。
- 確からしさで下げられるのは帰結が Major 以下のときだけ。回復不能な帰結はめったに踏まない経路でも Critical / Major を維持する。
- 防御的検査の追加提案（異常返り値・空 / `null`・切り詰め・ゼロ件・競合）は既定で Minor。
- 検証節・手順の堅牢化を狙う指摘は既定で Minor。Major になるのは本体の変更そのもの（対象ファイル・逐語アンカー・順序）が誤っているときだけ。
- 蓄積テスト: 閉じるリスクより、閉じるために開く対象面のほうが大きいなら Minor。
- 派生指摘（対症療法・横展開漏れ）は残るバグ自体の帰結で採点する。
- 動作中立な保守負債は Minor として残す。「本番では何も起きない」は報告しない理由にならない。
- simplification-review 由来の指摘は原則 Minor。振る舞いが変わるものだけ Major。Critical は出ない。
- 迷ったら 1 段上へ — Minor / Nit は独立検証を飛ばす経路があり、過小評価だけが精度フィルタを素通りする。

## クラス

- 2 値: AUTO-FIXABLE / NEEDS-USER。
- 代替案を 1 行で書けないなら NEEDS-USER でない。
- 根拠 か 決定記録 の 事実 から答えが 1 つに決まる問いは NEEDS-USER にせず、その答えを修正とする AUTO-FIXABLE にする。NEEDS-USER で届いたものは受け手が改める。
- 可逆な選択（語句・順序・理由の書き方）は AUTO-FIXABLE。
- 冗長・再掲・可読性の指摘への修正は削除・畳み込みだけ。言い換えの文や規則を弁護する理由節を足さない。

## 却下と判断との衝突

- 却下できるのは事実誤認のときだけ。価値が低い・コストが高い・リスクが高いは却下理由にならず、NEEDS-USER へ回す。
- 既存の判断との衝突の扱いは `plan-doctrine.md` の 判断行の書式。
- 事実の訂正は常に通す。

## Measurement

- 形は read-only の Bash 1 本＋期待出力、または fresh subagent への作業依頼文＋期待出力。
- 読み手行動型は「作業を与えて、打つコマンドを報告させる」形に限る。「この文をどう読むか」を答えさせる自己申告型は書かない — fresh subagent は文脈に無い文書を「ある」と答え、実測を捏造する。
- 打つのは受け手の main（code-review-to-plan / plan-refinement-loop の orchestrator）。
- 生成側が添えなかった Critical / Major には受け手が Measurement を書いて打つ。
- 結果は `plan-doctrine.md` の 事実 行の形にして finding-verifier の依頼文に添え、同じ行を 決定記録 の 事実 へ書く。
- 期待出力と不一致の Minor / Nit は落とす。Critical / Major は一致・不一致を問わず 事実 行にして裁定へ回す。

## 裁定（票勘定）

- 1 人目の finding-verifier が CONFIRMED なら確定。
- REFUTED / UNVERIFIABLE が出たら、まず事実の問いか価値の問いかを判定する。価値の問いは票で決めずユーザーへ。
- 事実の問いは 2 人目を足す。2 票で決まらなければユーザーへ。3 人目・多数決・打ち切り規則は持たない。

## 質問の出し方

- 推奨案を書かない。
- 本文に直接書く。コードフェンスや blockquote に入れない。
- 各選択肢に利点と欠点を書く。
- 利点・欠点の数を揃えない。片方が明確に劣るならその決定的な事実を 1 行書く。

## レビュー対象引数

- 対象トークンは 1 つ: commit range / PR・MR ref / ファイルパス。スキル固有引数（effort 等）を除いた先頭トークン。
- 既定（トークン無し）は未コミット + staged の和（`git diff HEAD`）。
- commit range は `git diff <range>`、PR・MR ref は `git-hosting/<hosting>.md` の「MR 差分」、ファイルパスはそのファイル全体を対象にする。
