# Finding Criteria

レビュー指摘の**重大度・クラス・拘束力・共通フィールド・質問の出し方**の正本。票の数え方（何票で決めるか・検証者を何人足すか）の正本は `adjudication.md`、どの重大度を検証へ回すか・収束条件は各スキルの領分であり、いずれもここには書かない。

- 生成側: standard-code-review / deep-code-review / simplification-review / plan-investigator。
- 受け手: code-review-plan-loop / plan-refinement-loop。
- finding-verifier は読まない — 根拠 だけを独立に検証する立場のため。
- **質問の出し方 節 だけは適用範囲が広く、レビュー指摘に限らずユーザーへ問いを出す側すべてに掛かる** — plan-writing（起案時に確定しなかった判断の提示）もこの節の読み手。

**この文書の目的は指摘の質を上げることであって、指摘を増やすことではない。** 重大度が1段上がるたびに再スイープ・独立検証・ユーザーへの照会のいずれかが発火する。採点は下流のコストを決める行為として行う。

## 重大度

**軸は「放置したときの帰結」×「その帰結が実際に起きる確からしさ」の2つ。** 実在確度（その指摘が事実か）と修正コストは別軸であり、重大度に混ぜない。

| 重大度 | 帰結 | コード差分での読み | プラン文書での読み |
|---|---|---|---|
| **Critical** | 放置すると回復困難な実害 | データ損失、セキュリティ侵害、本番停止・データ破壊 | そのまま実行すると破壊的（誤った対象、取り返しのつかない手順） |
| **Major** | **通常の実行経路で**誤ったものが動く・作られる | 通常の入力で機能が壊れる、バグが残る（対症療法・横展開漏れ）、呼び出し側の契約破壊 | 実装セッションが誤ったコードを書く・詰まる（誤ったパス/API/シグネチャ、必須手順の欠落、節どうしの矛盾） |
| **Minor** | 通常の経路では起きない、または動作が変わらない | 異常返り値・空/`null`・切り詰め等への防御不足、重複、再発明、回帰テスト欠落、曖昧な契約 | 実装セッションが書くものを変えない（冗長、解決可能な古い参照、明確さ） |
| **Nit** | 表記・語彙のみ | 命名、書式 | 言い回し（設計のやり直しは Nit ではない） |

採点規則（上から順に当てる）:

- **確からしさで下げられるのは帰結が Major 以下のときだけ。** 帰結が回復不能（データ損失・セキュリティ侵害・不可逆な手順）なら、めったに踏まない経路でも Critical/Major を維持する。
- **通常の実行経路で踏むかで Major と Minor を分ける。** 異常な返り値、空 / `null`、切り詰め、ゼロ件、競合といった防御的検査の**追加提案**は既定で Minor。「経路を説明できるか」ではなく「この変更を普通に実行して踏むか」で判定する（説明できる経路は常に書けるので、説明可能性は篩にならない）。
- **検証節・手順の堅牢化を狙う指摘は既定で Minor。** Major になるのは、本体の変更そのもの（対象ファイル・逐語アンカー・順序）が誤っているときだけ。
- **蓄積テスト: 閉じるリスクより、閉じるために開く対象面のほうが大きいなら Minor。** 条件を1つ足して閉じる指摘は、その条件自体が次のスイープの対象面になる — 帰結どうしの比較であって、修正コストの高低ではない。
- **起きえないことは指摘ではない。** `plan-doctrine.md` の 執筆規約 が禁じる「起きえないことの悉皆分析」は、書く側だけでなく採点側の基準でもある。防御を足す提案がその類なら報告しない。
- **仮説だけの指摘は成立しない。** 外部ツール・CLI の挙動を前提にした「壊れうる」指摘（出力が切られる・flag が効かない等）と、規則・手順文書への欠落指摘（記録先が無い・条件が無い・guard が無い）は、再現、実測または記録された失敗、一次ソースのいずれかを 根拠 に持つときだけ指摘として成立する。仮説だけなら報告しない — 仮説を塞ぐ手順・条件が積み上がり、写しと保守負債になる。受け手が合流時に採点するときも同じで、成立しない指摘は裁定へ回さない。対象外は、コードを実読して見つけた欠陥（当該行の実読が一次証拠）と、既存テキスト同士の矛盾（双方が一次証拠）。直前の 対象外（既存テキスト同士の矛盾を含む）に当たる指摘でも、害が「読み手・実装セッション・ツールがこう動く」という行動予測の形をとり、修正が文書へ文を足すものには、この規則が優先する: 機構の一次ソース（仕様文・ソースコード・既存テキスト）は「起こりうる」の証拠であって、**その経路を踏む**証拠ではない。この形の指摘は、生成側が `Measurement`（共通フィールド 節）を添えたときに成立し、Minor/Nit は受け手が実行して期待出力と一致したものだけが生存する。測定手順を書けないとき、Minor/Nit は報告しない。Critical/Major はこのゲートの対象外 — Measurement を添えられるなら添え（受け手が測る）、添えられなければ無しで報告してよい。削除・畳み込みで済む修正は測定を要しない — 足す側だけが証拠を要する。
- **派生指摘は元の欠陥の帰結を継ぐ。** 対症療法・横展開漏れの指摘は、残るバグ自体の帰結で採点する。
- **「本番では何も起きない」は報告しない理由にならない。** 動作中立な保守負債は Minor として必ず残す — 消すと横断・再利用の観点そのものが落ちる。
- **修正コストの高さ・価値の低さで重大度を下げない。** それらは採否の判断材料であって帰結ではない（採否は受け手の領分）。
- **迷ったら1段上へ** — ただし上の規則をすべて当てたうえで、なお決められないときだけ。Minor/Nit は下流で独立検証を飛ばす経路があるため、過小評価だけが精度フィルタを素通りする。

ponytail-review 由来の指摘は plugin が重大度を出さないため、simplification-review がこの表へ写像する: 原則 Minor、振る舞いが変わるものだけ Major。同スキルの担当は過剰実装のみで正しさ・セキュリティ・性能はスコープ外のため、既定で Critical は出ない。

## 実在確度（confidence）

重大度と**直交する別軸**。「この指摘は事実か」だけを測り、影響の大小や踏む頻度は含めない（それは重大度）。0-100 で採点するのは standard-code-review のみで、他の生成側は使わない。

- **75 以下** — 未確認の前提が1つでも残る（読んだだけの推測、実在は確認したが成立条件が未確認、成立条件まで確認したが決め手が一次証拠でない）。
- **100** — 一次証拠が直接それを裏付ける（当該行を実読、実行して再現、一次ソースで確認）。未確認の前提は残っていない。
- 誤検出と分かったものは採点せず、報告しない（篩は生成側の Never report であって、この軸ではない）。

しきい値 80 はこの2値の境界そのもの。Minor/Nit は 75 以下で破棄され、Critical/Major は破棄せず残す（破棄地点は生成側の領分であって、この節は値の定義だけを持つ）。confidence 80 を「Major 相当」と読み替えない — 高確度の Nit も低確度の Critical もありうる。

## クラス

- **AUTO-FIXABLE** — 客観的に正しい修正が1つだけで、好みの余地が無い。
- **NEEDS-USER** — 妥当な答えが複数あり、どれを採るかがユーザーの価値判断・スコープ・リスク姿勢に依存する。

NEEDS-USER へ上げる前のゲート（すべてを通ったものだけ上げる）:

- **代替案を1行で書けないなら NEEDS-USER ではない。** 書けない＝選択肢が実質1つ＝AUTO-FIXABLE。
  - 生成側の責務は分類して報告するところまで（read-only のものもある）。適用は受け手。
  - ただし**書けない理由が「正しい答えが分からない」ときは逆で、NEEDS-USER**。案がゼロなのと案が1つなのは別で、前者を AUTO-FIXABLE に落とすと未確定の判断が黙って確定する。
- **事実の問題は上げない。** 検証の票が割れたら、まず「事実の問いか、価値の問いか」を判定する。事実の問いは裁定手続きへ戻す（`adjudication.md`）。ユーザーへ上げるのは価値・スコープ・リスク姿勢の問い、または裁定で決着しなかった事実だけ。
- **可逆性で線を引く**（`document_type: implementation-plan` のとき）: 実装後に小コストでやり直せる選択（語句、順序、理由の書き方）は AUTO-FIXABLE。

**ゲートを全部当ててなお決まらないときだけ、迷ったら NEEDS-USER** — AUTO-FIXABLE の誤判定は、ユーザーの知らないうちに価値判断を代行して確定させる。

**却下できるのは事実誤認のときだけ。** 価値が低い・コストが高い・リスクが高いは却下理由にならない（手続きは `adjudication.md`）。

## 確定した判断の拘束力

修正を書くとき過去の決定をどこまで守るかは、**決定の種類と `（ユーザー判断: …）` マーカーの有無**で決まる。すべてを拘束すると制約が単調増加し、既存の主張を壊さないよう条件を足し続けることになる。

| 種類 | 拘束力 |
|---|---|
| **事実の訂正** | マーカーの有無を問わず拘束する。覆すと既知の誤りが復活する。訂正自体が誤っていた場合のみ、対抗する事実を示して覆せる |
| **見送り（やらないと決めたもの）** | マーカー付きは拘束する。**新証拠でその理由が成立しなくなったときだけ**再オープンでき、勝手に覆さずユーザーへ返す。マーカー無し（起案者の提案）は 設計・表現の選択 と同じ |
| **設計・表現の選択** | マーカー無しは拘束しない。より良い解が見つかれば1行の理由を添えて破棄・書き直してよい。マーカー付きは拘束し、より良い解があっても勝手に覆さず対案を添えてユーザーへ返す。事実誤認の訂正だけは対抗する事実を示して誰でも行える |

**同じ場所にパッチが積み重なったら、次の手当てはパッチでなく書き直し。** 事実の訂正 とマーカー付きの行だけ残し、それ以外の制約は捨てて、その項目を 目的 から書き直す。

**冗長・再掲・可読性の指摘への修正は、削除・畳み込みだけを既定とする。** 言い換えの文や規則を弁護する理由節を新たに足してよいのは、削除ではその指摘が解決しないと示せるときだけ — 足した散文は次のスイープの指摘母集団になる。

## 共通フィールド

指摘1件につき、生成側は最低限これを出す。**上乗せは自由**（生成側固有の観点行・修正案・confidence など）。

- **重大度** — 上のラダーの4値。
- **場所** — 逐語アンカー（対象ファイルに実在する引用文字列）。補助として `path:line`。欠落そのものを指す指摘のようにアンカーが取れないときは、挿入位置の直前・直後の逐語行を取り、それも無ければ `path:line` と節名を置いて取れない理由を 根拠 に書く。
- **問題** — 何が、なぜ問題か。
- **根拠** — 実際に何を確認したか（`file:line`、grep 結果、外部ソース）。問題 と同じフィールドに融合させない — finding-verifier は 根拠 だけを独立に検証する。
- **クラス** — AUTO-FIXABLE | NEEDS-USER の値。
  - 各案を 質問の出し方 節 の書式で書くのは**ユーザーへ提示する側**の義務。
  - 生成側が負うのは、提示素材まで出す契約を持つとき（plan-investigator → plan-refinement-loop）だけ。呼び出し元が解法の生成を止めている生成側（`修正案なし` を渡された deep-code-review）は案を書かない。
  - 受け手がこの値を合流時に落とすのは想定内（code-review-plan-loop の findings list は facts only で、採否のクラス判定は受け手が自分で当てる）。
- **Measurement**（任意） — 重大度 節 の「仮説だけの指摘は成立しない」規則が測定を要求する指摘だけが持つ。ツール挙動: read-only の Bash 1 本（素のコマンドで書く）＋指摘が成立するときの生出力の期待。受け手側の実行手順は `measurement-run.md` の 実行 節。読み手行動: 読ませる文書パス＋作業依頼文（「実行せず、打つコマンドを逐語で報告せよ」の形。クォート等の書き方のヒントを含めない）＋指摘が成立するときの期待出力。**行動型に限る** — 作業を与えて打つコマンドを報告させる。読み手に「この文をどう読むか」を答えさせる自己申告型は書かない（fresh subagent は文脈に無い文書を「ある」と答えて捏造した実測がある。2026-09-08）。生成側は書くだけで実行しない。

ID の採番は生成側ごと。複数ストリームが合流しても衝突しないよう、生成側ごとに接頭辞を付ける（合流後の dedupe と再採番は受け手の領分）: standard-code-review = `SC1..`、deep-code-review = `DC1..`、simplification-review = `PR1..`（内部で呼ぶ plugin は ID を出さないので、このスキルが振る）。plan-investigator は ID を出さない（受け手の plan-refinement-loop が `S1..` を振る）。

## 質問の出し方

NEEDS-USER（および plan-writing の 未確定の判断 のように、答えをユーザーしか持たない問い）をユーザーへ提示するとき、**推奨案を書かない**。推奨があるとユーザーがそれに引きずられ、フラットに選べない。

**本文に直接書く。コードフェンスや blockquote に入れない** — フェンス内は折り返されず、長い問いが横に伸びて読めない。

```
[U1] <場所> — <問い>
- A) <案>
  - 利点: <…>
  - 欠点: <…>
- B) <案>
  - 利点: <…>
  - 欠点: <…>

判断が分かれる点: <この選択を決めている軸を1行。どちらが良いかは書かない>
```

- 利点・欠点の数を揃える義務はない。片方が明確に劣るなら、その決定的な事実を欠点として1行書く — 均等配分を強制すると、劣る案が五分に見えて推奨より誤導する。
- 順序バイアス（先に読まれる案が有利）は消えない。緩和ではなく残余として認識しておく。
