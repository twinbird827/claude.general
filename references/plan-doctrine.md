# Plan Doctrine

プランファイルの姿勢・書式の正本。plan-writing / code-review-plan-loop / plan-refinement-loop の3スキルが起案前・entry で Read し、実装セッションも着手前に Read する共有資産。レビュー指摘の重大度・クラス・拘束力・質問の出し方の正本は `finding-criteria.md`、票の数え方は `adjudication.md`、どの指摘を検証へ回すかと収束条件は各スキルの領分であり、いずれもここには書かない。

## 姿勢

- **プランは実装セッションが読む唯一の文書**。載せるのは 目的 / 確定判断 / 修正内容 / 検証 の4つだけ。
- **指摘・裁定・却下・修正履歴はサイドカー `<plan>.review-state.yaml` へ**。プラン本文に書かない。プランへ書くと次のレビュースイープがそれを再レビューし、指摘が指摘を呼んで収束しない。例外が 目的 節 の指摘リスト（テンプレ 節）。載せるのは**このプランの 修正内容 が解決する指摘だけ**で、1行要約のみ（裁定・重大度・却下理由は載せない — それらはサイドカー）。別課題として起票したものとユーザーが見送ったものは 修正内容 に対応項目が無いため 目的 節 には載せない（載せると出口欠落として再指摘される。見送りの1行の書き先は本節の「意図的な省略・不採用の代替案・ユーザーが確定した見送り」バレットのとおり。起票したものはサイドカー `filed_issues` が記録なので本文には1行も残さない — `issue-filing.md`）。この対応関係はレビュー中も維持する — 対応する 修正内容 項目が消えたら 目的 節 の該当行も消す。
- **自己完結の目標は「判断とアンカー」**であって分析の網羅性ではない。実装セッションに要るのは、接地アンカー（対象パス・逐語引用・再利用資産）と、後戻り困難な確定判断。
- **完璧を求めない**。プラン段階で確実に潰すのは後戻り困難な判断のみ。取りこぼしは実装後の再レビュー（code-review-plan-loop）がバックストップで拾う — その案内が出るのは cr-loop 起案のプラン（収束ラウンドの最終プランを除く）と plan-refinement-loop を完走したプランだけで、他はユーザーが実装後に cr-loop を実行すれば同じ再レビューを掛けられる。プラン段階の取りこぼしは、plan-refinement-loop を走らせた場合にその精査が拾う。
- **意図的な省略・不採用の代替案・ユーザーが確定した見送りはプラン本文に1行だけ残す**（起案者の省略・不採用は項目単位なら当該項目の 理由 行、判断単位なら 確定済みの判断。ユーザーが確定した見送りは 確定済みの判断 のみ — マーカーの書き先がそこだけのため）。無記録の省略は次スイープで再指摘され収束を止める。レビュー指摘そのものの却下（事実誤認）は本文でなくサイドカー `rejected`。ユーザー確定の見送りは本文1行に加えてサイドカー `rejected` にも記録する（振動検知と次ラウンドの carry drop が参照するため）。例外は同型横展開スイープ（code-review-plan-loop）の除外ヒット: 同型でないため変えない箇所の記録は、理由 行でなく 検証 節 の当該再 grep 再実行手順に「除外: <箇所> — <理由>」を1行ずつ併記する（<箇所> の形は アンカー規約 節）。
- **分散した producer/consumer 契約（enum 値・対応規則・出力形式・キー定義 — 複数ファイル間か同一ファイル内かを問わない）に触れる変更セットは、正本1箇所へ集約し他を参照のみにする変更項目を、最初の独立項目として先行させる。** 分散を残して片側だけ直すと相手側との不整合が新たに成立し、二重管理箇所の数だけ後続の整合指摘が生まれる。
- **確定済みの判断 のうち `（ユーザー判断: …）` の無い行は起案者の提案であって既決ではない**（レビューループの AUTO 判断を含む）。実装セッションは着手前に一度だけ疑い、懸念があれば1〜2行で理由を添えて判断を仰いでから進む。無ければ何も言わず着手する。マーカー付きの行は覆さず書かれたとおり実装する（拘束の条件と例外は `finding-criteria.md` の 確定した判断の拘束力 節）。起案側はユーザーが答えた判断に必ずマーカーを付ける（テンプレ 節）— 付け忘れると実装セッションがユーザーの決定を提案として蒸し返す。

## 文書型

サイドカーの `document_type` を入力として受け取る。値は2つ。

- `implementation-plan` — 本文書の規約に沿って起案されたもの。
- `spec-or-design-doc` — それ以外（サイドカーを持たない手書き文書を含む）。

## アンカー規約

編集対象は**逐語アンカー**（対象ファイルに実在する引用文字列）で指す。行番号は補助であって指示ではない。

- 書く: 「`**Follow the plan-writing conventions**` で始まる段落を … に置き換える」
- 書かない: 「`:208-210` を移送する」— 行範囲の切り貼り指示は対象が1行ずれるたびにプランが偽になり、レビューが行番号監査に化けて収束しない。
- 新規ファイル・挿入ブロックは**プランに逐語で全文を書く**。「〜相当の内容を書く」と要約しない。ただし**変更内容から導出される派生テキスト**（履歴エントリ、Issue・MR 本文の説明文）は本バレットの対象外 — 逐語化すると本体の変更ではなくその写しがレビュー対象になり、主眼がずれる。場所 は通常どおり書き（MR 本文のように repo 外が対象なら、逐語アンカーでなく対象を同定できる記述でよい）、変更 行を「どこへ何を反映するか」の1行にとどめ、文面は実装セッションが書く。
- **対象ファイルが hard wrap しているときは、改行を跨がない範囲でアンカーを取る** — 跨ぐと継続行のインデントまで再現しない限り `old_string` が一致しない。hard wrap は規約で禁止だが（`CLAUDE.md` の markdown の書式 節）、blockquote は規約の除外で、未整形の既存ファイルにも残っている。fenced code block の中身は改行そのものが構文なので、この改行を跨がない制約の対象外 — アンカーは fence の内容を逐語でそのまま取る。
- **検証 節 の再 grep 手順が挙げる箇所も同じ規約に従う** — 除外行（姿勢 節）の <箇所> と、再実行後に残るべきヒットの列挙は、逐語アンカー（見出し・step 名を含む）で指す。

## 執筆規約

理由は**1行**。次の5項目は書かない: 代替案の網羅比較（採用案＋却下理由1行で足りる）／事実の付録重複／セクション再掲のチェックリスト／「起きえないこと」の悉皆分析／自分自身のレビュー履歴。

手順のコマンドは**意図と制約で書く**（例: 「未追跡ファイルがある — 本スキル自身の生成物 `docs/plans/` と `.tmp/` は除く — なら促して終える」）。除外条件・分岐元・完了条件のような**判断**は実装セッションへ委ねず書く。**逐語コマンドを書くのは次の3つだけ**: (1) 記録された失敗から学んだ非自明な形（「そのコマンドでないと壊れる」証拠を1行添える）、(2) 他ファイル・検証節と共有する契約（同じ grep パターンを検証節も再実行する等）、(3) permission の allow が前方一致で依存する形。それ以外の逐語は写しになり、外部ツールの挙動変更のたびに全写しの修正になる。

## テンプレ

以下のブロックは書式の例示であって、プラン本文をフェンスで囲む指定ではない。

```markdown
# 実装プラン: <name>
> 対象: <差分範囲・branch・commit / 起案元>

## 目的
<何を達成するか 1-3 文。レビュー起案なら「以下の指摘を解決する」＋**修正内容 が解決する指摘だけ**の1行要約リスト（姿勢 節 の例外。各行に `F1:` 等の ID を付す。欠番可、採番規則は各スキルの領分）>

## 確定済みの判断
<後戻り困難な判断を1行ずつ。ユーザー確定分は末尾に `（ユーザー判断: <一言>）`。無ければ節ごと省略>

## 修正内容
### 1. <一行サマリ>
- 場所: <逐語アンカー。補助として `path/to/File.ext:123`>
- 変更: <何をどう変えるか。確定設計・コード骨子はここに逐語で>
- 理由: <1行>

## 検証
<回帰テスト / 確認手順。修正内容 に項目があるなら、末尾に「実装後の反映: `~/.claude/references/mr-workflow.md` の手順に従う」の1行を置く（手順・分岐はその文書が持つ。ここにも各プランにも再掲しない）>
```
