# プランファイルの規約

プランは、別セッションが会話を持たずに実装できる文書。plan-writing が起案し、plan-refinement-loop が精査し、code-review-to-plan がレビュー結果から書く。置き場は `docs/plans/`（settings の `plansDirectory`）。

## 姿勢

- 完璧を求めない。プラン段階で潰すのは後戻り困難な判断だけ。
- 変更は差分の小ささでなく修正後の簡潔さで選ぶ。規則に例外・但し書きを継ぎ足さず、規則を書き直して例外を消す。既存構造・後方互換の維持も目的にしない — 既存がダメなら壊す変更を書き、維持するなら理由を 1 行書く。
- 理由は 1 行。代替案の網羅比較、事実の付録重複、節の再掲、起きえないことの悉皆分析は書かない。
- 判断は決定者を問わず暫定であり、順守事項でない。判断と衝突する指摘が出たら、判断を守るために解法を歪めず、衝突をそのまま出す。
- 実装セッションは着手前に 確定済みの判断 を一度だけ疑い、衝突があれば 1〜2 行で指摘してから進む。

## 構成

先頭に `> 対象: <差分範囲・branch・commit / 起案元>` の 1 行。節は次の 6 つだけで、順序もこのとおり。

1. **目的** — 課題と達成条件。レビュー由来のプランでは、この 修正内容 が解決する指摘だけを 1 行要約で列挙する。対応する 修正内容 項目が無い行は置かない。
2. **要ユーザー判断** — 未決の問いがあるときだけ置く。提示した選択肢を利点・欠点ごと逐語で書く（書式は `review-criteria.md` の 質問の出し方）。回答が来たら 決定記録 の 判断 へ 1 行で移し、この節から消す。節が空になれば節ごと消す。
   - 回答を移すとき、回答と衝突する句がプラン本文の他の箇所（決定記録 を除く）に残っていれば、同じ反映で直す。
3. **確定済みの判断** — 修正内容 が依拠する前提の判断。起案時の意図的な省略・不採用の代替案もここに 1 行ずつ。
4. **修正内容** — 変更項目の列挙。各項目は 変更 / 理由 の 2 フィールド。
5. **検証** — 実装後に何をどう確かめるか。
6. **決定記録** — レビュー中に確定した事実と判断。書式は下の節。

目的 / 確定済みの判断 / 修正内容 / 検証 には、このプランに対するレビュー履歴（スイープの指摘・裁定・修正の経緯）を書かない。残すのは 決定記録 の 1 行だけ — 本文に書くと次スイープの再レビュー対象になり、指摘が指摘を呼んで収束しない。

## 修正内容 の書き方

- 変更: 何をどう変えるか。2 段の入れ子の箇条書きで書く。
  - 1 段目に対象ファイルのパスを置き、2 段目にそのファイルへの変更を 1 行 1 件で置く。同じ文面の変更は 1 行にまとめてアンカーを並べる。ファイルをまたぐときは 1 段目にパスを並べて 1 エントリにする（同じファイルが複数の 1 段目エントリに出てよい）。
  - 2 段目の各行は、編集対象を逐語アンカーで行の中に指す。他の行やフィールドを「上記」で参照しない。
  - `path:line` は補助であって指示ではない。対象ファイルが hard wrap しているときは改行を跨がない範囲でアンカーを取る。fenced code block の中身は改行そのものが構文なので改行を跨がない制約の対象外 — アンカーは fence の内容を逐語でそのまま取る。
  - 新規ファイルはアンカーを置かない。
- 理由: 1 行。
- 挿入内容・新規ファイル・コマンドは意図と制約で書く。逐語で書くのは (1) 記録された失敗から学んだ非自明な形 (2) 他ファイルと共有する文字列・契約 (3) permission の前方一致が依存する形 の 3 つだけ。
- 変更内容から導出される派生テキスト（履歴エントリ、issue / MR 本文）は書かない。
- 分散した producer / consumer 契約に触る変更セットでは、正本 1 箇所へ集約する項目を先に置く。

## 判断行の書式

確定済みの判断 と 決定記録 の 判断 で共通。

- 1 判断 1 行。決定者と理由を添える: `<判断>（AI 判断: <理由>）` または `<判断>（ユーザー判断: <理由>）`。
- 同じ論拠の再指摘は落としてよい。新しい論拠を伴う指摘は判断を覆す候補として扱う。
- AI の判断との衝突: 新しい論拠が立てば AI 自身が覆してよい。覆した記録を 決定記録 の 判断 に残す。
- ユーザーの判断との衝突: NEEDS-USER へ「前回の判断: X / 今回の反論: Y」の形で出す。自動では覆さず、自動では守らない。

## 決定記録 の書式

プランの最後の節。1 行 1 記録。小節は 事実 と 判断 の 2 つ。

### 事実

- 実測結果: コマンド（または依頼文）の逐語、期待出力、判定に使った生出力（長ければ先頭 N 行と N）、一致したかの 1 行。
- Context7 等で確認した外部仕様。
- 起票した issue 番号。
- 同型横展開の除外ヒット: `除外: <逐語アンカー> — <理由>`。
- 事実は、差分がその前提を無効化しない限り真として扱う。

### 判断

- 却下（事実誤認。反証つき）、見送り、設計上の選択、覆した判断。
- 行の書式は 判断行の書式 のとおり。
- 未決の問いは判断ではなく 要ユーザー判断 節に置く。選択肢の逐語をこの節へ写さない。
